# S1: agent and shell status, pane variables, `ko shell` and `ko ssh`

Status: plan, 2026-10-30. S1 is the first stage of
[migration.md](migration.md) after P1. It is specified here as
[p1-mvp.md](p1-mvp.md) specifies P1: an implementer builds it from
this file and the named kido sources, without reading the rest of
kido first. The code rules of AGENTS.md apply. Every name in code that
moves is a ko name (decided 2026-10-30): `KO_*` variables, `ko_*`
shell identifiers, `ko-*` temporary directories, `share/ko`.

## 1. Scope

In:

- `ko-pane` reports OSC 133 steps, OSC 7501 reports, the foreground
  process and the active screen as control frames.
- The coordinator keeps each pane's shell phase, record set,
  foreground command and alternate-screen flag, runs kido's
  `Pane_status` rules once per change, and publishes the result as a
  `status` field on `GET /panes` and as a `status` event on `/client`.
- Pane variables: arbitrary client-set JSON per pane, with an HTTP
  API, limits and `var` events.
- `ko shell`: the primed login shell as the default pane command, and
  `ko shell -- CMD`.
- `ko ssh`: kido's ssh priming, with the mark as two pane variables.
- The shims `ko` and `ssh` in the ko bin directory, first on every
  pane's PATH.
- One status column in the terminal client's sidebar, with kido's
  glyphs and colours.

There are no `ko pane` commands (decided 2026-10-30). Variables are
set and read through the HTTP API only: by hand with `ko api`, and by
`ko ssh` calling the API directly.

Out, for later stages:

- The layout document, sessions, session headers (S2). In S1 the
  server still holds the flat pane set of P1.
- Runs, `ko.run`, the sweep, prompt delivery, the harness, `ko-pi`,
  indented subagent rows (S3).
- Kido.app (S5). Images, clipboard (S6). Remote attach (S7).
- Any tree. The server computes one `status` per pane and nothing
  across panes.
- The message and progress text in the terminal client's rows.

## 3. The server's new pane state

`Pane.t` gains these fields. All times are nanoseconds of
`CLOCK_MONOTONIC`, the clock `ko-pane` stamps its frames with and the
coordinator reads through a stub in `ko_server/native_stubs.c`
(`Luv` has no monotonic nanosecond clock on macOS).

| field | from | meaning |
|---|---|---|
| `last_prompt : int option` | OSC 133 `A` or `N` | when the last prompt started |
| `command : {started_at : int; line : string; running : bool} option` | OSC 133 `C`, `D` | the last command: its start, its line, and whether `D` has not arrived |
| `last_exit : {code : int; at : int} option` | OSC 133 `D` with an exit code | the last command's exit, cleared when the next `C` arrives |
| `records : Program_status.t` | OSC 7501 | the record set and its serial |
| `foreground : {pid : int; name : string}` | the foreground frame | the pty's foreground process group |
| `alternate : bool` | the alternate frame | the alternate screen is active |
| `vars : Vars.t` | the HTTP API | client variables |
| `track : Pane_status.track option` | `Model` | the status machine's state |
| `status : Protocol.status option` | `Model` | the last published status |
| `dirty : bool` | every event above | the model must run |

`Pane.command.running` is true from `C` until `D`. The heal rule of
kido (`State.shell` in `lib/state.ml`, "stuck C without D, healed by
the next prompt") becomes one line: an `A` or `N` sets `running` to
false. With nanosecond times there is no tie: kido's rule "a tie
resolves to running" (AGENTS.md, "OSC 133") has no case here.

`last_exit` copies kido's "captured last exit": kido reads
`#{pane_command_status}` and `#{pane_command_end_time}` from one tmux
read and keeps them as the Idle phase's `last` until the next command
is promoted, because tmux clears the status on `C`. ko keeps the same
shape: `D` with `has_exit_code` sets `last_exit`; `C` clears it.

## 4. The pane protocol additions

Frames use the framing of `ko_pane/protocol.h` and `Pane_proc.frame`:
`len u32` of what follows, `kind u8`, body; little-endian; a string is
`u32 len, bytes`. `ko-pane` sends these; the coordinator never
requests them. This file gives their layouts because their code does
not exist yet (protocol.md's rule); once `protocol.h` and
`pane_proc.ml` carry them, the code is the reference and this section
keeps only the rules. The same holds for the JSON shapes of sections
6.4 and 7 until `protocol.ml` has them.

    KO_PROMPT = 11
      step u8          1 prompt_start (A or N), 2 input_start (B),
                       3 output_start (C), 4 command_end (D);
                       libghostty-vt's GhosttySemanticPromptKind values
      prompt_kind u8   libghostty-vt's GhosttySemanticPromptPromptKind;
                       the coordinator ignores every step 1 whose
                       prompt_kind is not 0 (primary)
      has_exit u8      1 when D carried an exit code
      exit i32         the exit code, 0 unless has_exit
      at u64           CLOCK_MONOTONIC ns when the callback ran
      command string   the decoded command line for step 3, else empty

    KO_RECORD = 12
      state u8         0 idle, 1 working, 2 done, 3 blocked, 4 error,
                       5 clear; libghostty-vt's GhosttyProgramStatusState
      kind u8          0 none, 1 permission, 2 question, 3 auth
      progress i8      0 to 100, or -1 for none
      id string        empty for the root record
      app string       empty when the report had none
      title string     decoded, empty when absent
      msg string       decoded, empty when absent
      title_set u8, msg_set u8   1 when the report carried the field,
                       so an empty title and an absent title differ,
                       as in the fork's program_record

    KO_FOREGROUND = 24
      pid u32          the foreground process group of the pty, 0 if
                       tcgetpgrp failed
      name string      the process name: proc_name(pid) on macOS,
                       /proc/<pid>/comm on Linux; empty if unknown

    KO_ALTERNATE = 25
      on u8            1 when GHOSTTY_TERMINAL_DATA_ACTIVE_SCREEN is the
                       alternate screen

`ko-pane` registers `GHOSTTY_TERMINAL_OPT_SEMANTIC_PROMPT` and
`GHOSTTY_TERMINAL_OPT_PROGRAM_STATUS` beside the title and pwd
callbacks, always; there is no flag that turns callbacks off. A
callback appends its frame to
`p->events`, as `string_event` does; the frames go out with the next
`head` or on the poll turn, after the record that carried the bytes.
libghostty-vt validates a report before the callback
(`terminal.h`, GhosttyTerminalProgramStatusFn): ko stores what it
receives and parses nothing. A `CLEAR` report reaches the coordinator
as state 5. libghostty-vt sends one `CLEAR` with an empty id before
the `RESET` callback on RIS, so RIS needs no extra frame.

**The foreground check** runs only on events, never on a timer
(decided 2026-10-30): after every step 3 and step 4 frame, and after
a pty read when at least 100 ms passed since the last check. It calls
`tcgetpgrp` on the master, resolves the name, and sends
`KO_FOREGROUND` only when the pair changed from the last sent pair. An
idle pane never wakes for it. The one loss: a program that starts
with no output under a shell without integration is seen at its first
output. `ko ssh` is unaffected, because the integrated local shell
sends `C` when ssh starts. A pane sends one `KO_FOREGROUND` after
`ready`, so the coordinator knows the shell.

**The alternate check** runs after every `vt_write`: it reads
`GHOSTTY_TERMINAL_DATA_ACTIVE_SCREEN` and sends `KO_ALTERNATE` when
the value changed. The first value is primary and is not sent.

## 5. The record set

`ko_server/program_status.ml` keeps, per pane, the rules of the fork's
`program-status.c` and kido's `Program_status.parse` (AGENTS.md,
"Native agent status"; docs/design-program-status.md, "OSC 7501
records"):

- A record is `{id; state; app; title; msg}` with `state` one of
  `Idle`, `Working of int option`, `Done`, `Blocked of {kind; progress}`,
  `Error`, as `lib_tmux/program_status.ml` defines. `kind` is
  `Permission | Question | Auth option`; `progress` is `None` for -1.
  `app`, `title` and `msg` are `None` when the report had no field
  (`title_set`, `msg_set`; `app` when empty).
- The set holds at most **64** records (`PROGRAM_RECORDS`). A new
  record over the limit removes the one updated longest ago.
- **The unchanged-record rule:** a report whose id is in the set and
  whose state, kind, progress, app, title, msg, `title_set` and
  `msg_set` equal the stored record changes nothing: no serial, no
  event, and no move in the eviction order. Otherwise the stored
  record is removed and the new one appended, which makes it the
  newest.
- A `clear` with an empty id removes every record. A `clear` with id
  `x` removes `x` and every record whose id starts with `x/`. A clear
  that removes nothing changes nothing.
- A prompt start (step 1, primary) removes every record whose state
  is not `done` or `error` (the fork's `program_status_clear(wp, 0)`).
  Pane death and RIS remove every record.
- The set's `serial` starts at 0 and increases by one on every change.
- The published records are sorted by id, bytewise. A `working`
  record with progress 0 and no app, title or msg is dropped from the
  published set (kido's `parse` filter), not from the stored set.
- `root` is the record with the empty id. `app t r` is the app of `r`,
  else of its nearest ancestor by `/`, else of the root, else `None`.
  `forest` builds the child rows for the app's sidebar: records with
  a non-empty id, sorted by path, nested by prefix, with `depth`.

## 6. Status

### 6.1 Classification and titles

`ko_server/pane_kind.ml` is `lib/pane_kind.ml` over `Pane.t`
(docs/design-program-status.md, "Pane kinds"). In order:

1. `vars["ssh.dest"]` is a JSON string `user@host` with one `@`, and
   `foreground.name` is `ssh`: `Ssh {user; host; pane}`. `pane` is
   `Remote_agent {name}` when the root record's app is `pi` or
   `claude-code`, else `Remote_terminal`. The split is at the **last**
   `@`, so `deploy@realm@next.test` is user `deploy@realm` and host
   `next.test` (`ssh_mark_test.go`).
2. The root app is `pi` and `vars["pi.session"]` is a non-empty JSON
   string: `Pi_agent {session; name; inbox; activity}` with `name`,
   `inbox` and `activity` from `vars["pi.name"]`, `vars["pi.inbox"]`
   and `vars["pi.activity"]` when they are JSON strings, else `""`.
3. The root app is `claude-code`, or `pi` without the session
   variable: `Some_agent {name = app}`.
4. Else `Terminal`.

A variable that is not a JSON string counts as absent. The trust rule
is the gate above and nothing else: a stale `pi.session` on a shell
pane is no agent; a stale `ssh.dest` after ssh exits is no `Ssh`.

`title` (`Pane_kind.title`): `Some_agent` and `Remote_agent` use the
pane title, or the app name when the title is empty. `Pi_agent` uses
`pi.name`, or the pane title when the name is empty. `Terminal` and
`Remote_terminal` have none here; their row title is section 6.4's.

### 6.2 The shell phase

`ko_server/pane_status.ml` is `lib/pane_status.ml` with these
substitutions. Read the original for the full machine; the inline
tests move with it and must print the same expectations.

- `now`, `since`, `started_at`, `ended_at` and `at` are nanosecond
  integers. `debounce` is 200,000,000 ns.
- `reading` (kido's `reading ~transport p`) takes the pane's fields of
  section 3 in place of `State.shell`, `command_start`, `last_exit`,
  `last_prompt` and `command_line`:
  - `transport` and `command` present: `Command {command = line;
    started_at; prompted = last_prompt <> None}`.
  - `transport` and no command: `Unintegrated`.
  - `command.running` and `command` present: `Command {...; prompted =
    true}`.
  - not running, `command` present, `last_exit` present:
    `Exited {code; command = line; started_at; ended_at = at}`.
  - not running, `last_prompt` present: `Prompt`.
  - no `last_prompt`: `Unintegrated`.
- Running is promoted after `debounce` since the command was first
  observed, or at once when the alternate screen is on; until then the
  previous `Idle` is reported, so a short command never shows running
  (docs/design-program-status.md, "OSC 133"). Promotion clears `last`
  and any retained outcome from before the observation.
- `fullscreen` is `Pane.alternate`.

`Pane_status.pending t` is true while a command waits for promotion.
The model (6.5) then arms one 200 ms timer for that pane.

### 6.3 Agent status and outcomes

`core`, `advance`, `representative`, `report` and `observe` move
unchanged in logic: blocked > working > idle with ties by bytewise id;
the representative in the order blocked, working, the retained
outcome's record, idle, any; an outcome when a record enters `done`
or `error` from another state or absence, with the set's serial; an
unchanged final record never re-arms; the outcome shows at aggregate
idle and waits while something works; tracking resets when the root
app, the pi session or the ssh destination changes
(docs/design-program-status.md, "OSC 7501 records"). `label` gives a
`Terminal`'s title: the representative's `title`, else its `app`, else
`foreground.name`.

The `interactive` latch of `Ssh {Remote_terminal}` is kept: it becomes
true once `last_prompt > command.started_at`, and `reading` then runs
with `transport = false`, so the remote shell's markers give the
phase. Before it, the pane is a running command `ssh`.

### 6.4 The published status

`Model` writes `Pane.status`:

    status: {
      kind:    <Pane_status.kind as lib/pane_status.ml's yojson_of_kind>,
      program_status: {serial, records: [{id, state, app?, kind?,
                       progress?, title?, msg?}]},
      title:   string,
      message: string | null,
      progress: int | null,
      since:   int
    }

- `kind` is the typed status: `["Terminal", {phase, report}]`,
  `["Some_agent", {name, status}]`, `["Pi_agent", {session, status}]`
  or `["Ssh", {user, host, pane}]`, exactly as kido's RPC contract
  encodes `lifecycle`'s `Live.status` today (`share/rpc/contract.md`,
  "Item node"), with times in nanoseconds.
- `program_status` is `Program_status.yojson_of_t` of the published set.
- `title` is the row title: `Pane_kind.title` when it gives one; for
  a `Terminal`, the running non-fullscreen command's line when the
  phase is `Running` and there is no report, else `label`; for a
  `Remote_terminal`, `ssh user@host`, and `: <line>` appended while
  `interactive` and a non-fullscreen command runs. These are the rules
  of `bin/kido_sidebar.ml`'s `title` and `command`, moved into the
  server because Kido.app and the terminal client both show them.
- `message` and `progress` are the caption's inputs: the agent
  status's `msg` and progress for an agent kind, the report's for a
  shell kind; `null` when absent. The terminal client does not show
  them in S1.
- `since` is the status's `since`.

### 6.5 The model tick

`Model` runs when any pane is dirty, at most once per 16 ms per
server, and never otherwise: a dirty mark arms one 16 ms `Luv.Timer`
if none is armed; the timer runs `Pane_status.observe` for every
dirty pane with `now` from the monotonic clock, clears the marks,
compares the new status JSON with `Pane.status`, and on a difference
stores it and broadcasts the `status` event. A pane whose `observe`
leaves a pending promotion arms one 200 ms timer that marks it dirty
again. An idle server with idle panes arms no timer.

## 7. HTTP API additions

### 7.1 Rows

`GET /panes` rows gain:

    foreground: {pid, name}
    status:     <6.4> | null       null until the model ran once
    vars:       {name: value, ...}

### 7.2 Variables

    GET    /panes/pane_N/vars            -> 200 {name: value, ...}
    GET    /panes/pane_N/vars/<name>     -> 200 <value>  |  404 not_found
    PUT    /panes/pane_N/vars/<name>     body: one JSON value
                                         -> 200 {}
    DELETE /panes/pane_N/vars/<name>     -> 200 {}  (also when absent)

Rules:

- `<name>` is UTF-8 without control characters, 1 to 256 bytes,
  percent-decoded from the path. A longer or invalid name is
  `invalid` (400).
- The body must parse as one JSON value; `Content-Type` is not
  checked. A value over **1 MiB** of encoded JSON, a pane whose
  variables would exceed **8 MiB** in total, or a pane with 1,024
  names receiving a new name is `invalid` (400) with the message
  `variable too large`, `pane variables too large` or
  `too many variables`.
- A `PUT` whose value equals the stored value changes nothing and
  sends no event.
- An unknown pane is `not_found` (404). A dead pane keeps its
  variables until it is removed.
- Every change sends, on every registered `/client`:

      ["var", {pane, name, value}]        set
      ["var_deleted", {pane, name}]       deleted

  as `Protocol.client_event` constructors `Var` and `Var_deleted`,
  encoded as jsonkit's compact variants like every other event.

- The server reads only `pi.session`, `pi.name`, `pi.inbox`,
  `pi.activity`, `ssh.dest` and `ssh.args`, in `Model`, under 6.1's
  gate. Any change of a variable marks the pane dirty.
- Variables live in `Pane.t`. They go when the pane is removed and
  when the server stops. The upgrade state file (S9) will carry them.

### 7.3 Status events

    ["status", {pane, status: <6.4>}]

  the constructor `Status` of `Protocol.client_event`.

Sent only for the pane whose status changed. Both events are text
messages on `/client`, after `welcome`, in the order the server
produced them. A client that connects reads `GET /panes` for the
current values; there is no replay.

### 7.4 The server's command line

`ko server` gains `--bin-dir DIR`, the ko bin directory to put first
on every pane's PATH; without it the server uses
`Bin_dir.own ()` from `ko_shell/bin_dir.ml`, the directory beside the
installed executable (`<prefix>/share/ko/bin`), and nothing when a
checkout build has none. `--shell PATH` keeps its meaning and is
exported into the pane as `KO_SHELL` so `ko shell` resolves the same
shell.

## 8. Commands

Every command takes `--server DIR`. Errors print `ko <name>: <message>`
on stderr and exit 1, as `bin/ko.ml`'s `run` does. `ko shell` and
`ko ssh` are programs that run in panes, not API wrappers; a variable
is set by hand with `ko api`:

    printf '"deploy@example.test"' | ko api -X PUT --input - /panes/$KO_PANE/vars/ssh.dest
    ko api /panes/$KO_PANE/vars
    ko api -X DELETE /panes/$KO_PANE/vars/ssh.dest

`ko api` finds the server from `--server`, else `$KO_SOCKET`'s
directory inside a pane, else the default directory (P1).

### 8.1 `ko shell [-- CMD ARG...]`

From `lib/shell.ml` and `lib/prime.ml`, with these changes: no tmux
options are read; the shell is the first executable of `$KO_SHELL`,
`$SHELL`, `/bin/sh`; `Bin_dir.own ()` is the ko bin directory.

With no arguments it execs the primed login shell:

- Mode: `Prime.local_mode ~dotdir ~env path`. `zsh` with any of
  `.zshrc`, `.zshenv`, `.zprofile`, `.zlogin` in `$ZDOTDIR` else
  `$HOME` is `Zsh`; `bash` that answers `4.4` or newer to the version
  probe is `Bash`; else `Plain`.
- `Zsh`: a temporary `ko-shell.XXXXXX` directory (0700 files 0600)
  with `.zshenv` and `integration.zsh`; `ZDOTDIR` points at it;
  `KO_ORIG_ZDOTDIR` carries the user's `ZDOTDIR` when set; argv is
  `path -l`. The `.zshenv` restores `ZDOTDIR`, sources the user's
  `.zshenv`, removes the directory, and sources the integration at
  the first `precmd`.
- `Bash`: `env.bash` and `integration.bash` in the directory; `ENV`
  names `env.bash`; argv is `path --login --posix`. `env.bash` leaves
  posix mode, sources `/etc/profile` and the first of
  `.bash_profile`, `.bash_login`, `.profile`, then the integration,
  then removes the directory.
- `Plain`: no files; argv is `-<basename>` (a dashed argv[0]).
- Both integrations end with `Bin_dir.path_prepend_script`: the ko bin
  directory first on PATH, once, after the login files.
- A failure to write the files falls back to `Plain`.

With `-- CMD ARG...`: for a shell named `bash`, `zsh`, `sh`, `dash` or
`ksh`, exec `path -l -i -c SCRIPT path CMD ARG...` where SCRIPT is the
PATH prepend script followed by `exec "$@"`; for any other shell exec
`CMD` directly with `execvp`. No priming, no integration.

Every `kido` identifier in the moved shell code is renamed: the
functions `ko_osc133_precmd` and `ko_osc133_preexec`, the flag
`ko_osc133_ran`, the `_ko_*` locals, the `KO_ZSHENV` and `KO_BASHENV`
heredoc tags, the `ko_*` bootstrap names.

### 8.2 `ko ssh ARG...`

From `lib/ssh.ml` and `bin/main.ml`'s `ssh` body:

1. Find the real ssh: `Bin_dir.look_path_past ~path ~dir "ssh"` when
   the ko bin directory exists (the first `ssh` on PATH after the bin
   directory's entry that is not the shim), else `Fs.look_path`. None
   is `ko ssh: no ssh on PATH past <dir>`, exit 1.
2. `tty` is whether stdin is a character device.
3. Parse the arguments with `parse_ssh`: options before and after the
   destination, `--`, the option letters that take a value
   (`BbcDEeFIiJLlmOoPpQRSWw`), and the remote command. The tables of
   kept, dropped and refused letters are docs/design-program-status.md,
   "The ssh mark".
4. When `$KO_PANE` and `$KO_SOCKET` are set: run `ssh -G ARG...`; on
   exit 0 with `user` and `hostname` lines, send
   `PUT /panes/$KO_PANE/vars/ssh.dest` with the JSON string
   `"<user>@<hostname>"`, and `PUT .../ssh.args` with the connection
   arguments as a JSON array of strings when `ssh_connection_args`
   accepts them, else `DELETE .../ssh.args`. `ko ssh` sends these
   itself through `Ko_tui.Api.request` on the socket named by
   `$KO_SOCKET`, with the `Ko-Protocol` and `Ko-Vt` headers, and a
   2 s deadline. A failed or refused request is ignored, and never
   stops ssh. The variables are never unset afterwards.
5. Exec: when `tty`, the arguments parse, there is no remote command,
   and none of `N T W f s n O Q V G` is among the option letters, exec
   `ssh <opts> -t -- <dest> <bootstrap>`; else exec `ssh ARG...`
   unchanged.

The bootstrap is `Prime.ssh_bootstrap` as it is: both integrations as
single-quoted base64 in a POSIX sh script that primes a remote zsh
with dotfiles or a remote bash 4.4 or newer, and otherwise execs the
login shell plain (docs/design.md, "Priming a remote shell"). Its
identifiers are `ko_*` and its directory `ko-ssh.XXXXXXXX`.

### 8.3 Environment variables

| variable | set by | read by |
|---|---|---|
| `KO_STATE_DIR`, `XDG_STATE_HOME` | the user | every command (P1) |

## 9. The shims

`share/ko/bin/ko` and `share/ko/bin/ssh` with `share/ko/shim.sh`, from
`share/bin/kido`, `share/bin/ssh` and `share/shim.sh`, with `kido_*`
renamed `ko_*`. `ko` execs `<prefix>/bin/ko` relative to the shim
(`$0/../../../bin/ko`). `ssh` execs `<prefix>/bin/ko ssh "$@"`. The
`tmux` shim is not copied. `ko_real NAME` finds the first `NAME` on
PATH after the shim directory that is not the shim itself, and exits
127 with `ko: no NAME on PATH after <dir>` when none.

The server puts the bin directory first on every pane's PATH, before
`ko shell` runs, as kido's launcher does for the tmux server
(docs/design.md, "The bin directory"); the integration puts it first
again after the login files. `Bin_dir.of_exe` tries the unresolved
executable path first (AGENTS.md, "Installed-file lookup").

`share/dune` installs `share/ko/bin`, `shim.sh`, `bash/` and `zsh/`
beside `bin/ko` and `bin/ko-pane`.

## 10. The sidebar status column

`ko_tui/sidebar.ml` rows become `N <mark><title>`: the index, one
space, one column for the status mark, the title. The mark column is
always present, so titles align. Width stays 24; the row text is cut
at the width.

The mark is kido's `indicator` of `bin/kido_sidebar.ml` over the
pane's `status.kind`, without the tree and the run cases, with kido's
glyphs and colours (decided 2026-10-30). The rest of the sidebar
stays as P1 draws it: no colours, no styles, the shown or chosen row
in reverse video across the width.

| indicator | mark | colour | when |
|---|---|---|---|
| Running | `◼` | green, `Ansi.Color.green` | an agent `Running`; a shell with a report `Running`; a shell phase `Running` that is not fullscreen |
| Waiting | `◆` | yellow bold, `Ansi.Color.yellow` | an agent `Waiting`; a report `Waiting` |
| Done | `✓` | green bold | an unseen success outcome; an unseen exit with code 0 and no report |
| Failed | `◼` | red, `Ansi.Color.red` | an unseen failure outcome; a report `Idle` with an unseen non-zero exit; an unseen non-zero exit |
| none | ` ` | | idle with nothing unseen; a fullscreen phase; an unintegrated shell |

The colours and the two bold marks are the defaults of
`bin/sidebar_theme.ml` (`error`, `running`, `waiting`, `done_`) as
indexed SGR colours, so the outer terminal's palette applies
(p1-mvp.md 5, "Colours"). The `@kido-sidebar-*-style` options are
not carried over. Every mark cell sets `fg` explicitly (AGENTS.md,
"Mosaic"); every other sidebar cell keeps the default `fg`. On the
reverse-video row the mark keeps its glyph and loses its colour: the
cell is drawn with the default `fg` and `inverse`, like the rest of
that row, as kido strips the colours of its selected row. A dead
pane keeps P1's ` †status` after the title.

**The seen rule** (`bin/kido_sidebar.ml`, `unseen` and `observe`):
the client keeps, per pane, the outcome key `(source, serial)` and
the exit key `(started_at, ended_at)` that it last showed while the
pane was the shown pane. On every `status` event for the
shown pane, and on every switch, it stores the current keys. An
outcome or exit whose key equals the stored key is seen. An exit that
ended before the client started is seen. Thus a visit acknowledges,
and a later outcome with a new serial shows again. The state is the
client's; nothing goes to the server.

kido's 0.5 s hold that keeps a finished command's row green is
dropped (decided 2026-10-30): it covered tmux's polling, and events
arrive at once.

## 12. Done criteria

- Every test of section 11 passes in `make verify`; the kido suite
  stays green (nothing in `lib/` changed).
- An idle server arms no timer: `TestNoIdleWakeups`, and a 10 s
  `sample` (macOS) or `strace -c` (Linux) of the coordinator with
  idle panes shows no wakeup from `Model`.
- `Model` runs at most once per 16 ms per server under a flood of
  OSC 7501 reports from 20 panes, and the event count equals the
  status changes, measured by a test that counts events against
  reports.
- A status change reaches `/client` within 20 ms of the report under
  no load (the 16 ms tick plus the hop), measured with the echo tool
  of `bench/client.py` extended with an OSC 7501 round trip.
- `ko ssh` and `ko shell` behave as `kido ssh` and `kido shell` on the
  same machine, shown by the moved tests.

## 13. Decisions taken on 2026-10-30

1. The status marks keep kido's glyphs and colours, with `fg` set
   explicitly for each mark; the rest of the sidebar stays without
   colours, with reverse video for the shown or chosen row (10).
2. The OSC 7501 record set lives in the coordinator; `ko-pane`
   forwards each report (5).
3. kido's 0.5 s green hold is dropped (10).
4. There are no `ko pane` commands. Variables go through the HTTP API
   only: `ko api` by hand, and `ko ssh` calling the API directly (8).
   `ko shell` and `ko ssh` stay as programs that run in panes.
